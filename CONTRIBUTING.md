# Contributing

From the guidebook: "Małe pushe i jasne granice dają więcej niż wielkie scalanie na koniec."
Small pushes, clear ownership, no big-bang merge at the end.

## Roles (4 roles, 1 repo)

- **Kapitan / Product** — owns scope and the clock, resolves disputes, doesn't code.
- **Builders (1-2)** — own their module/screen, small commits, frequent pushes.
- **UX / Data** — screens, copy, demo data. Figma/Canva or UI prompts.
- **Pitch / Research** — competitive scan until 15:00, then only the pitch script.

## Rhythm

| What | When |
|---|---|
| Push | every ~30 min |
| Pull | before you start a session |
| Demo direction | shared, agreed once |
| Feature freeze | 15:45 — after this, fixes only |

## Rules that prevent the classic mistakes

1. **One person, one folder.** Agree who owns which piece and the shared data shape before writing code.
2. **Don't touch someone else's file** without asking first — a "typo fix" that overwrites an hour of someone's work is the #1 hackathon regret.
3. **Push often, don't wait for a perfect end-of-day merge.** If a conflict happens: agree out loud who takes the header, who takes the styles, and resolve it live.
4. Not writing code today? Use GitHub Desktop — `File > Clone repository`, commit/push from the button, no terminal needed.
5. Using Claude Code / an agent? It's fine not to know git — just say "commit and push" or "pull the team's changes."

## Before you build anything

- [ ] Say in one sentence who this is for and why they'd use it.
- [ ] There's a moment in the demo where someone thinks "I want this."
- [ ] It's demoable without slides or a verbal setup.
- [ ] It can grow in 8 hours — it doesn't need 8 weeks.
